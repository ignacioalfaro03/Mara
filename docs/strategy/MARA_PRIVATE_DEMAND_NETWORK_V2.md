# MARA — PRIVATE DEMAND NETWORK V2

Status: Product strategy + execution contract  
Effective: 2026-09-08  
Parent authority: `MARA_PRIVATE_DEMAND_NETWORK_FOUNDER_AMENDMENT.md`

> **MARA CONVERTS PRIVATE DESIRE INTO AGGREGATED DEMAND, AND AGGREGATED DEMAND INTO PRODUCTS, EXPERIENCES AND ECONOMIC OPPORTUNITIES.**

---

# 1. CATEGORY

Mara is evolving toward a:

# PRIVATE DEMAND NETWORK FOR CREATOR WORLDS

The core market primitive is not a post, event or SKU.

It is **demand**.

A user can express what they want before supply exists. Mara can group similar demand, measure economic strength and help the relevant Creator / Host / Operator / provider fulfill it.

Creator Worlds are the first high-density context for this network because they already contain identity, culture, audience and recurring desire.

---

# 2. CORE LOOP

`WORLD → COMMUNITY → WANT → PLEDGE → COMMIT → AGGREGATED DEMAND → SUPPLY → UNLOCK → TRANSACTION → FULFILLMENT → MEMORY → RETURN`

User-facing action:

# MAKE IT HAPPEN

Prompt:

> **What do you want to happen?**

The user should not need to classify the request perfectly. Mara can progressively structure it.

# 4. DEMAND SIGNAL LADDER

## WANT

Low-friction signal.

User says:

> I want this too.

No payment claim.

## PLEDGE

User states willingness to pay around a value.

This is stronger than WANT but still not a transaction.

## COMMIT

Strong synthetic / future commercial signal.

In production this may later map to provider-supported authorization, reservation or purchase intent only after legal, payment and refund gates are closed.

## UNLOCKED

The relevant demand threshold is reached.

Do not collapse these signals into one count.

- PLEDGE_CREATED;
- COMMIT_CREATED;
- DEMAND_UNLOCKED;
- PURCHASE_COMPLETED;
- FULFILLMENT_COMPLETED;
- EVENT_ATTENDED;
- CONTRIBUTION_SELECTED.

MVP proof:

# MY HISTORY

Later:

# SINCE YOU LEFT

Examples:

- a request you joined is close to unlock;
- your World approved something you wanted;
- you helped unlock a drop;
- a collection changed;
- an IRL request in your city crossed threshold.

---

# 10. PRIVACY

Privacy is a product differentiator.

Conceptual demand visibility / identity modes:

## PUBLIC
Demand can be discovered publicly. User identity can still remain minimal.

## PSEUDONYMOUS
Demand is visible while participant identity is represented by alias / aggregate only.

## PRIVATE
Restricted or invite-only demand pool.

Long-term operational principle:

# VERIFIED PSEUDONYMITY

Mara may verify identity internally when required while exposing minimum necessary information externally.

No promise of perfect anonymity.

No sale of identifiable individual demand history.

# 11. VIP REVENUE ARCHITECTURE

VIP is intentionally future-facing in this V2.

Product families:

## EVENT VIP
Priority, hospitality, limited zone, collectible, early access.

## CREATOR INNER CIRCLE
Recurring membership around belonging, early access, voting, limited opportunities and World status.

## MARA GLOBAL VIP
Cross-World priority and premium service after network liquidity exists.

## PRIVATE GROUP
Small, curated group experience with higher ARPU.

## MARA CONCIERGE
High-value request where Mara coordinates supply for a defined brief and budget.

VIP sells scarcity, curation, service, privacy and production quality.

VIP never changes consent boundaries.

# 12. HOST MARKETPLACE — FUTURE

Hosts are future supply-side professionals.

Potential progression:

`COMMUNITY HOST → VERIFIED HOST → SENIOR HOST → OFFICIAL CREATOR HOST → MARA CERTIFIED PRODUCER`

Host value proposition:

> **There is validated demand. Can you fulfill it profitably and safely?**

Future Host object can include:

- verified status;
- alias / business identity;
- cities;
- specialties;
- fee;
- capacity;
- rating;
- completion rate;
- creator endorsements;
- safety / incident record;
- repeat bookings.

Do not build the production Host marketplace before demand behavior is validated.

---

# 13. ROLE MARKETPLACE — FUTURE

Members may progressively become supply.

Progression:

`FAN → CONTRIBUTOR → TRUSTED MEMBER → PAID ROLE → HOST`

Potential roles:

- event assistant;
- community moderator;
- greeter;
- production assistant;
- authorized photographer;
- thematic performer;
- host assistant;
- creator representative.

Principles:

- community participation and operational labor are different;
- recurring responsibility should not be disguised as free fandom;
- compensation must be transparent;
- reputation can remain pseudonymous externally;
- payment does not create consent.

Future flow:

`DEMAND → CREATOR/IP APPROVAL → HOST → VENUE → PREPAYMENT → RULES → QR → EXPERIENCE → PAYOUT → REVIEW → MEMORY`

Possible building blocks:

- Creator licensing;
- official Host designation;
- venue marketplace;
- Mara Pass / dynamic QR;
- ticketing;
- access levels;
- VIP;
- privacy rules;
- ratings;
- payouts;
- incident reporting;
- post-event memory.

Founder constraint:

> **MARA ORCHESTRATES. THIRD PARTIES FULFILL.**

Do not become a manual event-production agency.

---

# 15. SAFETY / CONSENT / ADULT BOUNDARY

For any adult-oriented or physical category:

- adults only where required;
- identity / age verification where legally appropriate;
- creator/IP authorization;
- Host / venue verification;
- explicit rules;
- incident reporting;
- no coercion;
- no illegal services;
- no assumption of physical or sexual access from payment;
- no hidden labor exploitation.

Canonical rule:

> **A PAYMENT OR TICKET NEVER PURCHASES ANOTHER PERSON'S CONSENT.**
